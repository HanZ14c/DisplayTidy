# macOS 显示器布局工具：项目说明

> 暂未确定应用名称。本文是开发参考，描述计划与验收要求，不代表功能已实现或兼容性已验证。

## 项目目标

开发一个自用的原生 macOS 菜单栏小工具，精确调整多个显示器的位置，保存常用布局并一键恢复。支持外接显示器，以及已经通过随航（Sidecar）连接、作为扩展桌面使用的 iPad。

典型场景：连接外接屏或随航 iPad 后，从菜单栏选择「书桌」或「iPad 在左侧」，恢复屏幕排列；临时改变摆放时，通过「右侧 + 垂直居中」快速调整。

## 平台与技术栈

- 仅支持 macOS，建议最低版本 macOS 13；在建立项目时确认开发机器的版本。
- Swift：业务逻辑和位置计算。
- SwiftUI：菜单栏弹窗内容、布局列表、编辑界面及排列预览；SwiftUI 应用生命周期直接管理原生 MenuBarExtra(.window) 与设置场景，AppKit 应用委托监听屏幕变化并同步菜单栏图标可见性。
- AppKit：屏幕名称、屏幕识别浮窗及必要的窗口管理。
- Core Graphics / Quartz Display Services：显示器枚举、位置读取、布局提交和变化监听。
- Foundation：Codable、JSON 文件存储；UserDefaults 保存少量偏好。
- Xcode：构建、调试和生成本地 `.app`。

优先使用系统框架。第一版无需后端、账户、网络服务、数据库或第三方依赖。

## 第一版范围

### 显示器信息

显示当前活动屏幕的名称、尺寸、位置和主屏标记。使用编号浮窗帮助用户识别实体屏幕。扩展桌面是第一版支持的工作模式；遇到镜像屏幕，明确提示该状态并阻止不适用的独立排列操作。

### 相对位置与对齐

用户选择目标屏幕、参考屏幕和相对方向：

- 左侧或右侧：顶部、垂直居中、底部对齐。
- 上方或下方：左边缘、水平居中、右边缘对齐。

第一版一次调整一个目标屏幕相对于参考屏幕的位置，所有屏幕均可充当任一角色，但不能互相相同。保留系统主屏身份；主屏作为移动目标时，对计算后的全布局统一减去主屏的新原点，保持主屏位于 (0, 0) 以及所有非目标屏幕之间的相对位置。计算后先验证布局，再提交给系统；非法重叠或不连通的方案应提示原因，不能悄悄调整其他屏幕的相对位置来补偿。

### 排列记忆与收藏

只保存由程序设置的明确排列关系：目标屏幕 UUID、参考屏幕 UUID、方向和对齐方式。不保存任意手动拖动的位置，也不从系统坐标推断用户意图。刷新时允许按实际坐标精确匹配固定对齐以更新界面；未匹配时显示实际位置，不保存推断关系。当前应用支持相对所选参考屏的四个方向、每侧三种对齐，共 12 种方式，记住最后一次成功应用的关系；多个命名排列留到 M2。图形选择器显示待应用的两屏示意，不是当前实际多屏排列预览。按住扩展屏框显示候选，拖动时突出最近位置，松开后吸附到固定对齐，点击应用后才提交。图形下方的对齐菜单提供精确选择，不支持任意偏移。

每次应用都读取当前屏幕尺寸，按关系重新计算位置。重启后载入选择，但不自动移动。缺屏或身份不明确时提示重新选择；主屏改变时不自动切换主屏，由用户确认当前参考屏幕后应用新的关系。

### 应用与反馈

不提供原始坐标恢复或快照归档的日常入口。旧快照文件原样保留，不参与新的排列流程。

应用前校验关系与目标布局，提交前复核屏幕状态。失败时取消尚未完成的事务；完成提交后，无论返回成功或失败，都重新读取实际状态。实际布局是最终依据，不自动再次修改。只有位置验证成功后才保存新的排列关系，保存失败时明确说明屏幕已对齐但关系未保存。

### 设置与日志

主界面和菜单栏均提供设置入口，设置窗口包含独立日志窗口入口与开机自启开关。自启使用系统登录项，仅在用户切换开关时注册或取消注册；读取实际状态，显示系统批准提示和 API 错误，不自行开启。自启只启动菜单栏应用，不自动移动屏幕。

## 后续功能

- 随航快速换边。
- 屏幕连接后自动恢复匹配布局，默认关闭。
- 快捷键。
- 布局导入与导出。

第一版不包括自动建立随航连接、亮度控制、分辨率管理、窗口排列、实体屏幕尺寸校准、跨平台支持或 App Store 发布。

## 核心实现约定

### 坐标

布局逻辑统一采用 Core Graphics 全局桌面坐标。主屏原点为 `(0, 0)`，使用屏幕左上角坐标；左侧和上方可出现负坐标。不要混用 AppKit 的坐标方向、物理像素或画布缩放坐标。

例如 B 放在 A 右侧并垂直居中：

```text
B.x = A.x + A.width
B.y = A.y + (A.height - B.height) / 2
```

计算结果提交时统一取整：取最近整数，恰好半整数时向远离零的方向取整。画布只是该坐标系的缩放预览。

### 布局合法性

- 屏幕尺寸必须为正；任何两块屏幕的内部不能重叠。
- 两块屏幕只有共享至少 1 个桌面坐标单位的边缘才算相邻；仅角点接触不算连接。
- 以屏幕为节点、相邻关系为边，所有屏幕必须连通，允许通过其他屏幕间接连接。
- 单次移动只改变目标屏幕；其他屏幕保留坐标。若导致三屏布局不合法，应拒绝操作并解释原因。

### 读取与提交

候选 API：`CGGetActiveDisplayList`、`CGDisplayBounds`、`NSScreen`。

提交流程：

```text
读取当前状态 → 按保存的关系和当前尺寸计算 → 校验目标布局
→ CGBeginDisplayConfiguration
→ CGConfigureDisplayOrigin（同一事务设置相关屏幕）
→ CGCompleteDisplayConfiguration
→ 等待状态更新 → 重新读取实际布局 → 比对并反馈 → 保存关系
```

检查每一步的 `CGError`，提交前失败时取消事务。系统可能修正请求的位置以避免重叠或空隙，因此实际布局是最终依据。

开发初期使用 `.forSession`；是否使用 `.permanently` 在真实设备验证后再决定。应用保存的布局收藏与系统配置生效范围是两回事。

### 屏幕身份与随航

不要把运行时的 `CGDirectDisplayID` 单独当作永久身份。验证显示器 UUID 等信息是否可用且稳定；名称只能辅助匹配。同型号屏幕或虚拟屏幕匹配不明确时，要求用户指定对应关系。

随航必须实测：能否枚举、能否移动、有线/无线重连后身份是否稳定、显示尺寸变化后的恢复行为。不要预设公开 API 一定能可靠区分随航与其他虚拟显示器。

本应用管理已经连接的随航扩展屏。自动连接随航另行研究，不以私有 API 或自动点击系统设置作为第一版依赖。

### 变化监听

当前通过 AppKit `applicationDidChangeScreenParameters` 接收系统屏幕变化，更新菜单栏图标并刷新屏幕列表；应用正在提交排列时沿用 busy 保护，由提交过程确认实际布局。只刷新，不直接修改排列。未来需要更细的事件与合并控制时，再使用 `CGDisplayRegisterReconfigurationCallback`。

应用自己的修改也会触发回调。未来加入自动恢复时，必须避免重复应用和反馈循环。

### 数据保存

布局使用带 `schemaVersion` 的 Codable JSON，写入应用的 Application Support 目录并采用原子写入。损坏文件不能导致崩溃，也不能在读取失败后直接覆盖原数据。

## 最小代码组织

先使用少量文件：应用入口、DisplayManager、布局模型与 LayoutStore、SwiftUI 界面。纯位置计算可以单独提取，便于验证。

不提前创建插件系统、通用跨平台接口、依赖注入容器或只有一个实现的协议。只有真实复杂度出现后再拆分。

## 权限与分发

先构建当前用户运行的本地 `.app`，验证实际权限与 App Sandbox 行为。不要预先声称需要或不需要辅助功能、屏幕录制、管理员权限；核心位置功能不包含录屏或控制其他应用。

自用阶段优先通过 Xcode 构建运行。公开分发、Developer ID 签名、公证和 App Store 要求属于后续独立工作。

## 开发检查原则

- 对齐计算使用少量有意义的单元测试：负坐标、不同尺寸、居中取整、布局合法性。
- 系统 API、热插拔、睡眠唤醒和随航行为通过真实设备验证。
- 每次提交显示器配置后重新读取结果。
- 保留上次成功应用的关系；尺寸变化后重新计算，不恢复旧坐标。
- 尚未测试的硬件行为标记为「未验证」，不能用模拟测试代替兼容性结论。
